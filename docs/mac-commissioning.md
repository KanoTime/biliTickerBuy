## 连续执行的任务

### 1. 找到当前副本并核对环境

先定位这份仓库的已有本机副本，没有再克隆当前分支。检查工作区变更；不能覆盖用户配置或用强制重置清理。使用 Python 3.11 或 3.12 和独立虚拟环境，确认操作系统、arm64 架构和实际解释器。

安装项目依赖，运行 `pip check`、离线 `python -m app_cmd.goal demo`。随后启动原 UI，仅绑定 `127.0.0.1`，不启用公网分享。确认页面实际可打开，不能仅以进程存在判断成功。

常规安装、依赖和本地代码兼容问题可以直接修复并验证。不要为此重写框架、换仓库或开发另一套界面；不要把 Linux 已通过的证据当作本 Mac 已通过。

### 2. 取得两个账号的真实本机导出

优先复用本机已有、用户确认属于本目标的导出文件。缺失时使用原 UI 完成两账号登录和导出；需要本人扫码或官方验证时展示当前页面，说明具体操作，完成后继续。

两个账号分别选择 28 日普通票和同三位购票人；原 UI 还必须填写联系人姓名、电话并选取该账号的收货地址。不要因为是电子票就私自移除这些当前实现要求的字段。

两份导出只保存在本机。Cookie、手机号、完整姓名证件和整个响应正文不粘贴到聊天、Page、PR 或公开日志。账号 A/B 和人员 P1/P2/P3 足够用于汇报。

### 3. 自动填写可以确定的配置

使用 `import-exports` 从两份导出提取 UID 与买家 ID，不让用户重复手抄八个 ID：

```bash
python -m app_cmd.goal import-exports \
  --account-a /ABSOLUTE/PATH/account-a.json \
  --account-b /ABSOLUTE/PATH/account-b.json \
  --ends-at 'YYYY-MM-DDTHH:MM:SS+08:00'
```

将命令中的路径和结束时刻替换为本机实际值。A 导出中的三人顺序对应 P1/P2/P3。完整证件能够唯一对应时，程序自动匹配 B；仅有脱敏资料时，先在本机核对两份名单，使用 `--b-order` 指定 B 中分别对应 P1/P2/P3 的一基位置，例如 `--b-order 2,1,3`。不要按同名、证件尾号或两个列表的默认顺序猜测。

如果已有 `goal.toml` 或状态库，先读取和复用，不能通过重新生成配置或删除状态库绕开未决人员。导入器拒绝覆盖；必要修改在核对现有人员和状态之后完成。

已有明确的回流结束时间则复用。没有时，先完成其他准备，再只询问这一项实际缺失信息：用户准备守到何时、能够及时处理付款。不要猜测官方退款截止，也不要重新问已确定的日期、票种、数量、是否允许拆单或是否需要 fork。

### 4. 运行真实只读预检

依次运行：

```bash
python -m app_cmd.goal validate
python -m app_cmd.goal preflight
```

检查两账号分别是否 ready、固定目标和三人映射是否正确、运行窗口是否有效。记录每账号预检耗时及失败类别；预检只读登录、活动和购票人信息，不调用 prepare/create/支付接口。

如果失败，定位实际字段、业务码、验证要求或环境原因。修正常规问题后只重做受影响检查；禁止把失败泛化为“换个项目试试”，也不能通过放宽身份、日期、价格或未决状态校验来得到 ready。

### 5. 进入已授权的真实目标运行

固定目标、三人映射和运行窗口准备完整、只读预检通过后，可以继续用户已经授权的首发与回流任务：

```bash
python -m app_cmd.goal run --open-payment
```

让 Mac 在运行窗口内保持唤醒，确认本机系统自动校时开启，并记录实际启动时间。首发未完成后由同一循环守回流，不另外启动不共享人员状态的第二套抢票程序。

创建订单后提醒用户切到正确账号，在官方页面核对并付款。用户付款和官方验证需要本人完成时再交接，不把取得订单号写成最终已购三张。

若创建结果不明，保留占用，按指南核对官方订单；自动核验不足时使用 `stop → confirm → run --resume`。不要删除数据库重来。保持能够通过 `status` 查看、通过 `stop` 阻止下一次提交。
