# 两账号三人目标的本机使用指南

个人目标入口管理固定活动、日期、普通票档和三位购票人。首发先尝试三人同单；平台明确反馈所选数量不足且没有建单时，允许按 3 → 2 → 1 调整。售罄后继续等待同一票档回流，只为未购得且没有未决占用的人购买。

本次模板已经填入公开核实的 FES 目标：2026 年 11 月 28 日普通入场券、198 元、活动 `1006859`、场次 `1035758`、票档 `960028`。来源及读取时间见[公开目标记录](fes-target-20261114.md)。这些值会在每次实际尝试时重新核对，不从可点击状态推断库存数量。

## 取得当前分支并运行离线演示

以下命令在 Mac 的终端中、源码目录内执行。先确认 `python3` 是 Python 3.11 或 3.12；本轮自动化测试使用 Python 3.12。新入口需要当前 fork 分支中的代码。

```bash
git clone --branch codex-order-reliability-20261114 https://github.com/KanoTime/biliTickerBuy.git
cd biliTickerBuy
python3 -m venv .venv
source .venv/bin/activate
python -m app_cmd.goal demo
```

`demo` 仅使用标准库、临时状态文件和模拟平台。它演示三张不足、两张创建、最后一张售罄、回流后补齐及模拟付款确认，不登录或连接平台。输出中的 `mode` 为 `offline_demo`。

需要运行原有配置界面和真实平台适配器时，再在此环境安装项目依赖：

```bash
python -m pip install -e .
python main.py ui
```

已有本仓库环境可直接使用；保留本机配置和状态文件。Mac 图形界面、账号登录及真实订单回包仍需本机预演，本轮没有远程部署到用户设备。

## 准备两个账号的本机导出

在原有界面分别登录账号 A、B，读取本活动、选择 11 月 28 日普通票，并各自预选同样的三位购票人，使用“生成配置”功能取得两份 JSON。两份文件均应包含三人的完整选择，票面合计为 59400 分。

生成目标模板：

```bash
python -m app_cmd.goal template
```

随后把两份导出保存在 `btb_goal_data/account-a.json` 和 `btb_goal_data/account-b.json`。生成的 `btb_goal_data/goal.toml` 使用同目录相对路径。

只需在本机补齐以下内容：

| 字段 | 填写方法 |
| --- | --- |
| 两个 `uid` | 对应真实登录账号。导出 Cookie 中的 `DedeUserID`/`DSUserID` 可用于本机核对；在线预检还会检查实际登录 UID |
| 每个账号的 `buyer_ids.P1/P2/P3` | 填该账号导出 `buyer_info` 中相应人的 `id`；同一个 P1 在两账号必须是同一位真实购票人 |
| `mapping_confirmed` | 如果导出仅有脱敏证件或不能自动核对的证件格式，在本机确认三人对应关系后设置为 `true` |
| `ends_at` | 按自己能守候并及时付款的安排填写结束时刻，必须包含 `+08:00`，例如 TOML 中完整的北京时间格式 |

模板已设置开售时间 `2026-11-15T18:00:00+08:00`。结束时间不替用户猜测，也不等同于官方退票截止。调整结束时间不会清除已有订单占用。

凭据、姓名、证件和联系方式仅保存在本机导出文件中，不需要粘贴到聊天或 PR。`btb_goal_data/` 已加入 Git 忽略。状态库不保存这些原文；目标指纹使用规范化身份快照的整体摘要，防止换人后误用旧的已付状态。

## 先检查配置和只读预检

```bash
python -m app_cmd.goal validate
python -m app_cmd.goal preflight
```

`validate` 只读取本机文件，不连接平台、不建立订单状态库。它检查账号区分、固定目标、原始三人数与金额，以及两账号的购票人对应关系。

`preflight` 读取当前登录 UID、活动详情和购票人列表，不调用订单准备、创建或付款接口。活动详情本身可能使用只读业务含义的 HTTP POST，不能用 HTTP 方法名称判断是否下单。

发现账号、日期、名称、票价或实名映射不一致时，会给出对应字段；在本机修正后重新检查。短暂网络失败、服务端限流会被标为可延期，运行器按返回的等待时间重试。遇到官方验证要求，在官方页面完成验证。

## 启动首发及后续回流

保持 Mac 不休眠、网络连接稳定、系统时钟自动同步，然后运行：

```bash
python -m app_cmd.goal run --open-payment
```

程序等待配置的开售时间，随后由一个本地循环协调两个独立账号客户端。当前版本一次执行一个有界购买尝试；它支持账号接替和不同人组分工，没有开启双账号同时发送或底层 fanout。

每次实际创建前，都为本次人组重新 prepare、核对人数和固定金额、持久化提交意图，再检查停止标记及截止时间。首发后仍有空闲购票人时自动继续等待和购买，无需再启动一项捡漏任务。

创建订单后，输出账号别名、P1/P2/P3 人组、订单号和官方详情链接。`--open-payment` 会尝试打开该链接。按提示切换到对应账号核对并付款；打开页面或显示信息失败不会重新下单。

## 状态、停止和恢复

另开一个终端，进入同一源码目录并激活相同环境，可以查看或停止：

```bash
python -m app_cmd.goal status
python -m app_cmd.goal stop
```

也可以在运行终端按 Ctrl+C。停止会阻止后续创建；已经进入网络提交的请求仍需保存其返回结果。不要通过删除状态库或强制新建另一份状态库来处理未决订单。

| 人员状态 | 含义 |
| --- | --- |
| `available` | 尚未购得，没有未决占用，可继续购买 |
| `preparing` | 已取得本次人组，仍在准备，尚未授权创建 |
| `submitting` | 创建意图已保存，可能已向平台提交 |
| `pending` | 本程序已取得有效订单号，等待核对付款 |
| `unknown` | 是否建单不明，保留该人组占用 |
| `review` | 平台提示已有订单、重复或资格问题，需要核对 |
| `paid` | 已通过足够的官方订单证据或明确人工核验确认完成 |

重启会释放仅处于 `preparing` 的记录，把遗留 `submitting` 转为 `unknown`。待付款、未知和需复核的人不会因时间过去、重启或切换账号而重新变成空闲。

显式继续已停止的目标：

```bash
python -m app_cmd.goal run --resume --open-payment
```

`--resume` 保留原订单及人员状态。若已经超过 `ends_at`，先按自己的新安排修改结束时间；同一人的未决记录仍然保留。全部三人确认完成后，后续创建次数为零。

## 自动核验不足时的本机确认

自动核验目前只处理本程序成功创建并持久化绑定的已知订单号。它要求账号、活动、场次、人数、金额及付款/关闭字段满足[接口证据文档](goal-api-evidence.md)中的条件。当前账号缺少这些字段时，保留占用，不猜测已付款或未下单。

如果需要人工核对，先执行 `stop` 并等待运行进程退出；在官方订单中心确认具体日期、票档、购票人和状态，再记录结果。下列大写值是本机需要替换的参数：

```bash
python -m app_cmd.goal confirm --attempt ATTEMPT_ID --outcome paid --order-id ORDER_ID
```

`ATTEMPT_ID` 来自 `status` 中这组人的记录，`ORDER_ID` 是核实后的官方订单号。其他结果包括：

- `pending`：核实有匹配的待付款订单，绑定其订单号。
- `closed`：核实相应订单已经关闭、未付款，允许对应人组随后重新进入目标。
- `no_order`：明确核实这次未决尝试没有创建目标订单；已知待付款订单不能用此选项清除。

候选订单号只作为排查线索保存在记录说明中，未证明属于本目标时不绑定成目标订单。空订单列表或付款倒计时结束，均不足以自动记录 `no_order` 或 `closed`。人工结果记录为 `user_verified`，随后可使用 `run --resume` 继续剩余人组。

## 验证范围

本轮验证包含真实本地 SQLite 事务和进程锁、真实子进程离线入口、实际协调器配合模拟账号、实际平台适配器配合故障响应，以及原有订单结果修复的回归测试。公开活动详情的真实读取已确认本场目标字段。

尚未完成用户 Mac 上的安装和登录预演，也没有使用用户账号创建订单或验证本场认证订单回包。完整购票链的现场成功率、延迟和自动付款状态识别仍需据本机结果确认；当前实现不能保证放票或补齐三张。

运行器退出码 `0` 表示全部人员已确认完成，`3` 表示已停止但仍有未完成或待核状态；配置/命令错误使用 `2`。正常到达自己设置的结束时间且只购得部分，也会保留实际结果并结束。
