# 2026-11-15：从离线正确性转向实际购票准备

## 判断

上一版 `f073d6c1772e4991f9fc1654f93e9e72bf32232f` 已完成共享人员状态和正常回流流程，但出现了局部优化偏离最终目标的迹象：测试数量和状态处理逐渐成为主要进度指标，用户 Mac 的真实登录、首个创建请求的时序和部分成功后的继续购买尚未验证。

这些基础修复仍有必要。应保留有效订单号、固定日期票价、人员占用和重启恢复，把后续投入转向减少实际等待、解决会提前停住的分支，以及让用户的本机配置真正可用。不能用继续增加模拟测试代替一次真实本机预检。

## 已证实的问题和本轮修复

| 问题 | 对目标的影响 | 本轮处理 |
| --- | --- | --- |
| 每次尝试都重读登录、详情和全名单 | 刚完成预检也要多等串行身份请求 | 成功 UID 和逐人映射在同一账号实例内复用 30 秒；每次仍新读固定目标、重新 prepare |
| 三人不足、两人不足、先买到一人后，人数上限保持 1 | 即使随后能买两张，剩余两人也被拆成两笔，可能占满两个账号 | 成功创建部分订单或核实关闭释放人员后，重新优先当前剩余全组 |
| 补 P3 仍检查 P1/P2 的在线资格 | 无关人员的错误可能阻塞剩余人 | 实际尝试及恢复预检使用当前需购买的人组；本地全组身份绑定继续验证 |
| HTTP 200 内的只读业务异常被一律当作永久账号故障 | 临时读取失败后，账号不再恢复 | 未完成读取可以延期；明确登录、身份或资格矛盾仍阻塞 |
| 当前不可售与明确活动结束被合并 | 回流任务可能过早停止 | 当前不可售在运行窗口内等待并重新核对；明确结束仍停止 |
| 先同步查旧订单，再尝试剩余人 | 慢查询占用剩余人可购买的窗口 | 可用人组先尝试；每轮最多核验一笔并轮换，从查询完成时计算下次时间 |
| 自动核验不足的解释被丢弃 | 程序仍在运行，但用户不知道需要核对订单 | 去重显示账号、人员别名、订单及本机核验指引，不清空占用 |
| 固定一秒等待未对齐开售或下一次尝试时刻 | 可能额外推迟到下一次循环 | 等待最近的有效截止时刻，并保持停止响应 |
| 导出中已有 UID 和购票人 ID，却要求手填八个 ID | 增加准备时间和映射出错机会 | 新增本地 `import-exports`；完整证件唯一匹配才自动对应，脱敏情况要求明确的本机顺序确认 |

## 能证明的性能变化

同一离线场景先完整预检，再分别尝试 P1/P2 和 P3。直接加载原提交的适配器与本轮适配器，禁止 DNS、socket 连接和 UDP，使用相同模拟响应执行。

| 阶段 | 原版调用序列 | 新版调用序列 |
| --- | --- | --- |
| 显式预检 | 登录 → 目标 → 购票人 | 登录 → 目标 → 购票人 |
| 两人尝试 | 登录 → 目标 → 购票人 → prepare → create | 目标 → prepare → create |
| 一人尝试 | 登录 → 目标 → 购票人 → prepare → create | 目标 → prepare → create |
| 合计 | 13 次 | 9 次 |

目标读取在此模拟中代表一次成功详情请求。减少的是 **30 秒成功缓存有效期内的串行调用数量**，不是已经测得的真实毫秒数，也不是成功率提升百分比。显式 `preflight` 强制新读；缓存到期、未验证过的人员或失败后，恢复必要的身份读取。订单状态不缓存。

初始化若已到开售，只预检首个可用账号，备用账号在实际尝试时核对，避免首单继续等待备用账号。若长时间提前启动导致身份缓存已过期，首笔仍需重新验证；不能把短缓存描述成全天预热或永远两步下单。

当前仍为串行购买协调。共享同三个人时，同时向两个账号发送创建请求并不等同于增加有效购票机会。是否需要更多并发，应根据本机实际阶段耗时判断；本轮没有引入线程池、代理池或多副本抢同组人员。

## 实际安装与界面证据

在干净 Python 3.12、Linux 隔离副本中完成完整 `pip install -e .`，`pip check` 无冲突；实际解析得到 Gradio 6.32.0、Starlette 1.10.0。原界面构建 214 个组件，loopback 页面返回 HTTP 200，验证后关闭。仅关闭容器自动分享和打开浏览器，没有登录或调用购票接口。

使用原 UI 的真实 `on_submit_all()` 函数生成两份模拟账号导出，均包含三人、合计 59400 分；输入实际 `GoalAccount` / `GoalConfig` 后通过校验，并可构造仅 P3 的批次。这证明当前导出结构能够接入目标入口。

原界面生成配置仍要求联系人姓名、电话和收货地址，包括电子票。指南现已补充；本轮未擅自删改平台下单字段。

以上不是 Apple Silicon Mac 的实机验证，也不证明扫码登录、当前认证响应或付款识别已通过。

本轮修改后的 15 个受影响测试文件联合运行 **449 passed**；Ruff 检查、全库 114 个 Python 文件格式检查及 `git diff --check` 通过。它们是本次改动的回归门槛，下一阶段的主要验收仍是本机真实预检和购票结果。

## 下一阶段以什么作为结果

优先完成 [Mac 本机执行委托](mac-commissioning.md)：确认当前代码、安装与界面、两个实际登录账号、同三人映射、固定目标和运行窗口，运行只读预检。成功与失败都保留脱敏原因及实际耗时。

只有本机证据才能继续回答：首次提交授权距离开售有多长、目标读取与 prepare 哪一步最慢、是否触发验证、创建返回何种业务码、订单是否真实生成、付款与最终票据是否一致。新增日志中的提交授权时刻是程序回调时刻，不是服务器收到请求的时间。

本机预演完成后冻结无关功能；真实运行遇到具体失败再做针对性修复。HaTickets、大型统一界面、多日期多票档和重新选仓都不抢占当前 FES 准备时间。
